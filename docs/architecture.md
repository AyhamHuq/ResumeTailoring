# Resume Tailoring Architecture

## Overview

The app is a local-first resume tailoring workflow built around three guarantees:

- The LLM returns structured JSON only.
- Every generated claim is grounded in a parsed evidence card.
- DOCX output is generated by application code, never by model-authored XML.

The intended runtime stack is React and Vite in the browser, a local Node/Express API proxy for LLM calls, shared TypeScript/Zod validation, `mammoth` for DOCX-to-text parsing, and `docx` for ATS-safe resume export.

## Modules And Ownership

The source tree is organized by responsibility:

- `src/shared`: shared schemas, role modes, budget defaults, project and job ID validation, keyword synonym rules, and generated resume validation.
- `src/server`: Express routes, OpenAI-compatible provider adapter, prompt assembly, JSON parsing, validation, and one-shot repair flow.
- `src/client`: React workflow UI, braindump upload, local persistence, evidence review, keyword panel, resume preview, and DOCX export trigger.
- `data/config`: static profile metadata such as name, contact, education, certifications, employers, titles, dates, allowed role modes, and allowed project IDs.
- `tests`: Vitest contract tests for evidence parsing, validation, keyword classification, LLM repair, and DOCX export. These tests discover practical public helper modules and are expected to become active as implementation exports are added.

Static resume metadata is not generated by the LLM. It is loaded from configuration and merged with validated generated content at preview/export time.

## Runtime Data Flow

1. The user uploads the consolidated braindump DOCX.
2. The browser uses `mammoth` to extract text.
3. A deterministic heading-based parser converts the text into evidence cards.
4. The app verifies required sections are present: `CapTech Ventures`, `Publicis Sapient`, `Sallie Mae`, and `Additional Projects`.
5. Braindump text, evidence cards, filename, and update timestamp are persisted locally.
6. The user pastes a job description and chooses a role mode.
7. The client sends the JD, role mode, static profile, evidence cards, allowed project IDs, and section budgets to `POST /api/generate-resume`.
8. The server builds a strict prompt and calls the configured LLM provider.
9. The response is parsed as JSON and validated for schema, evidence refs, project IDs, unsupported claims, and budgets.
10. If validation fails, the server makes one repair call with the validation issues.
11. A validated resume JSON response is rendered in the preview and review panels.
12. DOCX export combines static profile data with validated generated content using a coded `docx` template.

## Evidence Card Format

Evidence cards are fact-level records derived from the consolidated braindump:

```json
{
  "id": "captech_f100_idempotency",
  "type": "work_project_fact",
  "parent_job_id": "captech",
  "project_id": "captech_f100_messaging",
  "title": "Idempotent direct messaging migration",
  "evidence_text": "SQS retry and reprocessing behavior used idempotency to prevent duplicate processing.",
  "skills": ["SQS", "idempotency", "event-driven architecture"],
  "metrics": [],
  "role_tags": ["backend", "cloud"],
  "source_heading": "Fortune 100 Direct Messaging Migration"
}
```

Stable IDs are part of the validation contract. Generated bullets must reference existing `evidence_refs`; broad job-level references are discouraged when a narrower fact-level card exists.

## LLM API Contract

`POST /api/generate-resume` receives:

- `jobDescription`
- `roleMode`
- `profile`
- `evidenceCards`
- `allowedProjectIds`
- `budgets`

The provider adapter is OpenAI-compatible and configured by:

- `LLM_API_KEY`
- `LLM_BASE_URL`
- `LLM_MODEL`

When no API key is present, the server may use mock generation for local UI testing. The mock response must still pass the same validation rules.

The model output is structured JSON containing `role_mode`, `skills`, `work_experience`, `projects`, and `keyword_report`. Every generated bullet includes `text`, `evidence_refs`, `jd_keywords`, `word_count`, `char_count`, and `estimated_lines`.

## Validation Rules

Generated resume validation rejects:

- Missing required schema fields.
- Unknown job IDs.
- Unknown project IDs.
- Evidence refs not present in the evidence card set.
- Resume claims containing terms that the keyword report marks unsupported.
- Bullets over word, character, or estimated-line budgets.
- Too many bullets per job or too many selected projects.

Validation failures are not silently corrected by truncation. The server sends the issues to the model once for repair; if the repair still fails, the API returns actionable validation errors.

## Keyword Scoring

Keyword scoring is local and evidence-aware. It extracts technical terms and noun-like phrases from the JD, normalizes grounded synonyms, and classifies each term into:

- `covered_in_bullets`
- `covered_in_skills_only`
- `supported_but_omitted_for_space`
- `unsupported`

Grounded synonym examples include:

- `OOP`: SOLID, state machine, command pattern, factory pattern.
- `CI/CD`: Jenkins, GitHub Actions, Vercel.
- `cloud monitoring`: CloudWatch Logs, CloudWatch Insights, alarms, logging, tracing.
- `vector search`: FAISS, OpenSearch, document vector store, RAG.
- `IaC`: CloudFormation, CDK, Ansible.

Synonyms are allowed only when supported by evidence cards. Unsupported JD terms should be surfaced in the review panel instead of inserted into bullets or skills.

## DOCX Export Strategy

DOCX export uses the `docx` package with a coded ATS-safe template:

- Single column.
- No tables.
- No text boxes.
- No icons or graphics.
- Contact information in body text, not headers or footers.
- Standard fonts such as Times New Roman or Calibri.
- Fixed section order: name/contact, education, work experience, skills, projects, certifications.

Static content comes from profile configuration. Generated work bullets, project bullets, and skills come only from validated resume JSON. If page budget is tight, project bullets should be reduced before core work-experience bullets.

## Local Setup

Use a shell where `node`, `npm`, and `git` are on `PATH`.

```powershell
npm install
npm run typecheck
npm test
npm run build
```

Create a local `.env` for provider settings:

```text
LLM_API_KEY=...
LLM_BASE_URL=...
LLM_MODEL=...
VITE_API_BASE_URL=http://127.0.0.1:3001
SERVER_PORT=3001
```

Run the app locally with:

```powershell
npm run dev
```

## Limitations

- Heading-based evidence parsing depends on consistent braindump section names.
- Keyword scoring is heuristic and is not a full ATS simulation.
- DOCX page-fit estimates can differ slightly between Word, Google Docs, and LibreOffice.
- The LLM repair flow intentionally makes only one repair call to avoid opaque retry loops.
- The master resume DOCX is not parsed at runtime; profile metadata must be kept current in config.

## Future Improvements

- Add a richer evidence-card editor for correcting parsed facts before generation.
- Add project-only regeneration and validated project swaps.
- Store multiple braindump versions with migration checks for stable IDs.
- Add DOCX snapshot or unzip-level assertions for template structure.
- Add provider-specific prompt telemetry without logging secrets or full personal documents.
- Improve keyword extraction with a curated technical taxonomy per role mode.
